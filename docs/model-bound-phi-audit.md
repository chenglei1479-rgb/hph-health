# Model-bound content and PHI release

Audited against main `62d0b9d` (#41) and the implementation in this PR. This is a public, source-derived technical inventory. It does not contain patient records or private requirements. Test names below use fictional data only; the frozen PHI holdout was not read.

Codex subscription amendment (2026-10-25): based on main `8e12392234911ad900127231bbf93d06b183776f` (#55). The boundary below replaces the former Codex subscription ban without changing detection rules. Earlier detector/evaluation sections describe the historical audit.

## Release boundary and failures

`src/main/phi/gate.ts:assertModelBoundRelease` is the common fail-closed entry behind `assertModelBoundTextReleased` / `releaseModelText`, `releasePromptContent`, `guardProviderBody`, and `releaseModelBoundValue`. It requires an explicitly installed gate, applies the existing machine approval, de-identification and confirmation behavior, and limits an asynchronous release/review to 60 seconds. An uninitialized gate, exception or expired review cannot return a payload. A late confirmation cannot resume a rejected send. The retry error uses the main-process translator bound to the application's locale owner; ja, zh-Hans and en are supported, with translations also supplied for the other shipped locales.

Detection logic **did change** in `phi/detect.ts:detectNames` (the `nextField`, `stop` and patient-pattern continuation boundary around lines 521–526): a continuation line beginning with an age, birthday, chart-number, sex or era/date field cannot be consumed as part of the patient name. This prevents overlap with a chart identifier from hiding the preceding name. Detection thresholds and high-risk retention policy were not changed. `phi/name-boundary.test.ts` covers fictional examples. The dev-only comparison against the current main is recorded below.

An unapproved machine still hard-refuses detected patient PHI; approved machines retain the existing vault-backed pseudonyms, date shifts, age generalization and per-message confirmation. High-risk original-text retention rules are unchanged. No bypass option or new external host was added. Recognition is rule-based, not a guarantee of anonymization. The detector still classifies short Japanese strings as names. A categorized ordinary-label vocabulary now narrows main's existing whole-string-name-guess exception for categorical/aggregate output and connector queries; unknown labels and bare names take strict release. This does not change detector thresholds. The complete final provider body is still rescanned.

The Node backend now installs `phi/desktop-confirmer.ts:createDesktopPhiConfirmer` from application composition. It forwards de-identified previews and application-translated labels through the existing authenticated `phi-review` native operation to the same Electron review page. Missing desktop capability, rejected/malformed responses, disconnects and timeouts block sending. The 60-second deadline cancels the native review; late confirmation cannot send. Per-item manual masking remains available. Previously the Node process did not bind the Electron confirmer.

API-key agent processes route model traffic through app-owned loopback bridges. Each bridge uses `settings/provider-fetch.ts:fetchProviderRequest` immediately before upstream HTTP. That boundary scans the complete provider body (including replayed history, system text, tool output and object keys), blocks opaque attachments, and overrides an inherited `Request` body with the released body. Provider HTTP supports JSON bodies; binary/multipart uploads are refused. Redirects remain disabled.

### Codex subscription boundary (base `8e123922`, main #55)

Before this change, `managed-codex` launched the native CLI/ACP adapter with an app-owned subscription home. `prepareCodexRuntimeHomeAuthentication` copied subscription credentials and an imported route into delegated homes. Native prompt assembly, file/skill reads, tool feedback, history replay and compaction could produce subsequent HTTPS or WebSocket requests invisible to ACP. Admission correctly blocked that entire route.

Now the backend planner selects `codex-subscription`; the transport owner fixes the destination to the existing ChatGPT Codex endpoint, ignoring imported routes and legacy transport preferences. Each request resolves subscription headers in main and then passes the complete serialized model body to the existing `fetchProviderRequest`/`sendPhiChecked` boundary. No API key setup or external network endpoint is added. The child receives only the random loopback token and uses the existing API runtime configuration, including disabled plugins/apps, native delegation, Shell, memories, analytics, updates and feedback. Skills are materialized in the credential-free API home. Delegated homes clear stale subscription auth and imported routes; they use ephemeral ACP authentication. A raw subscription passed directly to `prepareModelConfig` still throws the localized unguarded-connection error.

The loopback host accepts only authenticated POST `/v1/responses`. Native file uploads, model discovery, `/responses/compact`, other paths, and WebSocket upgrades cannot reach upstream through this boundary. Compaction implemented as a Responses body is scanned like every other request. Unsupported paths stay closed rather than falling back to native subscription transport. Opaque/binary/media content still fails closed. Subscription requests force `store: false` and streaming; account ID and bearer token are attached only by main. Missing/unsupported credentials fail closed; expired credentials return upstream auth failure with no native fallback (the existing sign-in flow must supply fresh tokens).

`codex-subscription-phi.integration.test.ts` executes the real planner → owner → loopback HTTP bridge → final gate with a stubbed upstream: clean SSE, both subscription discriminators/builtin ID, PHI in prompt/project instructions/history/attachment text/tool results after an initial clean send, gate fault/uninitialized/timeout, opaque content, invalid credentials, rejected native endpoints, and absent boundary. Tests assert zero upstream calls on faults and no PHI canary in released requests. `backend-resolver.test.ts` covers Side chat resolution, legacy transport preferences and unavailable reconstruction; `agent-framework/codex.test.ts` checks direct configuration refusal and credential/route-free Windows/delegated homes. These are local boundary tests, not a Windows installer or live quota acceptance. A new Windows package and Leo's subscription send test are still required before AI writing acceptance.

Doctor currently represents a disallowed connection as `not_ready`/`incompatible`; a distinct privacy-admission diagnostic label and live credential-refresh health are follow-ups. No prompts, allowlists, PHI thresholds, API-key onboarding, workflows, telemetry or installer identity are changed.

## jRCT / UMIN conclusion

- **Were staff/contact columns returned before? Yes.** The original `searchRegistryExport` mapped every CSV header into result records with `Object.fromEntries(headers.map(...))`. This included 研究責任者, 実施責任者, 所属, telephone, email and 問い合わせ先 if present.
- **Are those columns returned to the model now? No.** `MODEL_REGISTRY_COLUMNS` and `isModelRegistryColumn` allow only exact normalized non-personal headers. Every other header, including unfamiliar contact aliases, is excluded before matching and result construction. Tests cover both registries and malicious/unknown personal columns.
- **Other jRCT/UMIN import adapter? No.** Repository references resolve to the supplied-CSV tool and manual resource guidance; there is no separate live registry importer added here.
- Allowed fields are still untrusted free text. The agent-facing result goes through shared PHI release, and the final provider body is checked again. Local single-detail UI is unchanged. No online search, scraping, altered User-Agent, telemetry or new domain is introduced.

## Confirmation frequency: characterized, not changed

There is **no fixed maximum number of confirmation windows per agent turn**. With the production confirmer installed, `gate.ts:review` calls it even when `highlights` is empty, including empty gate-health checks. Each prompt release, complete provider-body release, tool preflight, query check and agent-facing result release can therefore prompt separately. Additional tool calls, notebook output fields and provider retries add more reviews. Concurrent notebook output release can also request multiple windows.

`phi/turn-review-count.test.ts` executes the actual ACP prompt executor, provider HTTP boundary and ConnectorService/ParserEngine with a local stubbed tool (no external search). It waits for the entire agent turn, including tool responses. For this specific no-PHI flow:

| Tool round trips | Provider HTTP sends | Confirmation calls |
| ---------------- | ------------------- | ------------------ |
| 0                | 1                   | 2                  |
| 1                | 2                   | 7                  |
| 3                | 4                   | 17                 |

In that fixture the count is `2 + 5 × tool_round_trips`: initial ACP prompt + initial HTTP body, then tool preflight + query release + query health check + tool-result release + next provider HTTP body. Every recorded preview has zero highlights. This is a measured example, not an upper bound; online tools also check URLs and can add prompts.

**Proposal only; not implemented in this PR:** keep automatic scanning, approval checks and fail-closed behavior at every boundary. Separate automatic validation from interactive consent so empty/clean health probes do not open a window. Present one combined review of newly detected PHI immediately before an outbound payload is authorized. Bind the decision to the exact released bytes, destination, project, machine-approval state and turn, with a short expiry; reuse a decision only for identical already-reviewed content at a later boundary. Changed content, new PHI, manual masking, approval changes or expiry require a fresh decision. Never introduce a session-wide “allow all” flag; review errors/timeouts still block. Native tool reads and later responses must continue to be scanned. This needs its own implementation and consent-invalidation tests before changing current behavior.

## Japanese export-header compatibility

Existing repository CSV examples use `ID,Title`; they do not establish a complete Japanese export schema. The review supplied the real header spellings `jRCT番号`, `UMIN試験ID` and `実施状況`. These are now explicit allowlist aliases, together with nonpersonal title/condition/intervention/date fields. `connector-builtins/src/japan-research.test.ts` has one fixture for each source using these header spellings and wholly fictional values. It searches by the Japanese ID column and checks that ID, title, status, disease, intervention and date remain, while 研究責任者, 所属, 電話, メール and 問い合わせ先 are absent and cannot affect matching. This is local schema compatibility testing; no live registry lookup or export download was performed.

## Bounded ordinary-label compatibility

`phi/ordinary-label.ts` holds the reviewed categories in code, not a runtime switch:

- Sex: 男性 / 女性 / 男 / 女 / その他 / 不明.
- Yes/no: あり / なし / 有 / 無 / はい / いいえ / 陽性 / 陰性.
- Disease: 肺癌 / 胃癌 / 糖尿病 / 高血圧 and the finite additional disease entries in `ORDINARY_LABEL_VOCABULARY`.
- Medical search: a finite list including 無作為化比較試験, 観察研究, メタ解析, 生存率, 化学療法, 免疫療法, 放射線療法, 有害事象, 再発, 予後.
- Ward/department: Japanese-script prefixes with 病棟 / 科 suffixes (for example 東病棟, 西病棟, 内科, 外科, 〇〇病棟, 〇〇科); no spaces, digits or punctuation. The suffix matcher alone never grants release.

Admission requires **both** vocabulary/suffix matching **and** main's existing whole-string name-guess predicate with no additional detected PHI. A known term containing a chart number or date therefore cannot qualify. The set is narrower than main: bare `山田太郎` is no longer exempt. Both bare and labeled names, chart numbers and era birthdays are masked or refused in the regression tests. There is no threshold change or new switch.

For an exempt label, the original text is first classified by `detectPhi`, then an empty-text `assertModelBoundTextReleased` call must complete successfully before the original is returned. This deliberately checks the installed scanner/vault, machine-approval reader, native reviewer and deadline without pseudonymizing a known label. Uninitialized, throwing or expired gates cannot return it. Other text goes through `assertModelBoundTextReleased` with its original content. A query changed by strict release is refused rather than sending the old query.

Notebook aggregate preservation is additionally restricted to a CSV-shaped table with ASCII identifier headers and data cells consisting only of vocabulary/suffix labels or numeric values; it must also meet the whole-string/no-other-PHI condition. Patient-row refusal is still applied first. Unknown textual cells, names and mixed PHI take strict release. No trusted annotation is attached to these values: later complete-provider-body scanning still applies.

`schema-only/label-release.test.ts` and `connectors/phi-query.test.ts` exercise the vocabulary, suffix forms, unknown labels, bare/labeled names, mixed identifiers, gate failure/uninitialized/timeout and zero send on failure. `schema-only/service.test.ts` restores the requested categorical/aggregate expectations. This change affects label handling only; the confirmation-frequency implementation is unchanged.
